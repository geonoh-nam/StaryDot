# 스크린타임 세션 편성 알고리즘 설계

작성일: 2026-08-25

## 1. 배경

부모는 아이의 스크린타임을 일정 시간으로 유지하고 싶어 하고, 아이는 영상을 계속 보고 싶어 한다. 두 요구는 정면으로 충돌한다.

이 앱은 충돌을 **시간 통제**가 아니라 **착지 설계**로 푼다. 영상 사이에 짧은 퀴즈를 넣어 수동 시청을 능동 참여로 전환하고, 마지막 영상 뒤에 오프라인 미션 카드를 제시해 아이가 스스로 화면을 떠나게 만든다. 결과적으로 부모가 설정한 총량은 지켜지고, 아이는 "빼앗겼다"가 아니라 "끝냈다"로 세션을 마친다.

## 2. 범위

**이 문서가 다루는 것**: 세션 편성 알고리즘 (백엔드 로직)

**다루지 않는 것**: UI/화면, 인증, 서버 인프라, 영상 수집 파이프라인, 실제 개인화 모델

산출물은 의존성 0인 순수 TypeScript 모듈이다. 부수효과가 없으므로 Expo 앱 내부에서도, Node 서버 API로도 코드 변경 없이 동작한다.

```ts
planSession(input: PlanInput): PlanResult
```

## 3. 용어

| 용어 | 정의 |
|---|---|
| 세션 | 부모가 설정한 예산 1회분에 해당하는 시청 단위 |
| 예산(budget) | 부모가 설정한 총 스크린타임 상한 (초) |
| 언더슛(underrun) | 예산에서 실제 편성 소요를 뺀 나머지. 항상 0 이상 |
| 밴드(band) | 최선 조합 대비 추가로 허용하는 언더슛 폭 |
| 브레이크(break) | 영상 종료 트리거로 제시되는 활동 지점 |

## 4. 시간 예산 회계

부모 설정값은 **총량 상한**이다. 퀴즈도 화면을 보므로 예산에 포함된다.

영상 k개를 편성할 때:

```
total(k) = Σ(영상 길이) + (k - 1) × QUIZ_SEC + MISSION_CARD_SEC
제약:      total(k) ≤ budget
언더슛:    underrun = budget - total(k)
```

**핵심 주의사항**: 퀴즈 개수는 영상 개수에 종속된다. 영상을 하나 더 넣으면 퀴즈도 하나 늘어 예산이 두 번 깎인다. 따라서 이 문제는 고정 용량 배낭문제가 아니라 **선택 개수에 따라 유효 용량이 변하는** 문제다. 이 점을 놓치면 반드시 예산 초과가 발생한다.

k=1인 경우 퀴즈는 0개이며 미션 카드만 붙는다.

## 5. 알고리즘

### 5.1 전체 흐름

```
1. 후보 필터링   (캐릭터 매칭 + 최근 시청 제외)
2. 랜덤 그리디   × K회 → 유효 조합 수집
3. 조합 중복 제거 (영상 ID 집합 기준)
4. 밴드 내 무작위 추출
5. 길이 내림차순 정렬
6. 활동 배치
```

### 5.2 후보 필터링과 단계적 완화

캐릭터가 일치하는 영상 중 최근 시청분을 제외한다. 제외 후 유효한 조합을 하나도 만들 수 없으면 제외 규칙을 한 단계씩 푼다.

| 단계 | 규칙 |
|---|---|
| 0 | 캐릭터 일치 AND 최근 `RECENT_SESSIONS`(2)개 세션에서 미시청 |
| 1 | 캐릭터 일치 AND 최근 1개 세션에서 미시청 |
| 2 | 캐릭터 일치 |

완화는 **조합이 비었을 때만** 발동한다. 아예 못 트는 것보다 반복 시청이 낫다.

### 5.3 랜덤 그리디 best-of-K

```
plans = []
K회 반복:
    pool = weightedShuffle(candidates, scoreVideo)
    chosen = []
    for v of pool:
        if chosen.length >= MAX_VIDEOS: break
        if total(chosen + v) <= budget: chosen.push(v)
    if chosen.length > 0: plans.push(chosen)
```

`weightedShuffle`은 Efraimidis-Spirakis 가중 표본추출을 쓴다 (`key = random^(1/w)` 내림차순 정렬). MVP에서는 모든 가중치가 1이므로 균등 셔플과 동일하지만, 개인화 점수를 붙일 때 코드 변경 없이 반영된다.

`MAX_VIDEOS`(5) 상한은 1분짜리 영상 10편 같은 조합을 막는 가드다.

### 5.4 왜 DP가 아닌가

정확한 DP로 최적해를 구할 수 있고 복잡도도 문제되지 않는다. 그럼에도 쓰지 않는 이유는 **최적해가 결정적**이기 때문이다. 같은 캐릭터 + 같은 예산이면 매일 똑같은 조합이 나온다. 아이용 앱에서 이는 치명적이다.

언더슛은 안전한 방향의 오차다. 목표는 예산을 넘지 않는 것이지 정확히 채우는 것이 아니다. 2분 덜 보는 것은 누구의 손해도 아니다.

### 5.5 밴드 내 무작위 추출 — 다양성의 핵심

`argmin`으로 최선 조합 하나를 고르면 탐색을 열심히 할수록 오히려 같은 답이 확실해진다. 따라서 선택 단계에도 무작위성을 넣는다.

```
best  = min(underrun)
band  = { p ∈ plans : underrun(p) ≤ best + BAND_SEC }
result = uniformRandom(dedupe(band))
```

**중복 제거가 반드시 선행되어야 한다.** K회 중 50번 발견된 조합과 1번 발견된 조합을 그대로 섞어 뽑으면 "우연히 발견되기 쉬운 조합"이 50배 유리해진다. 그리디 특성상 긴 영상 조합이 여기 해당한다. 영상 ID 집합을 키로 중복을 없앤 뒤 균등 추출한다.

`BAND_SEC`는 다양성과 예산 활용률을 맞바꾸는 단일 손잡이다.

- 좁게 → 예산 알뜰, 조합 고정
- 넓게 → 조합 다양, 시간 남음

어느 쪽으로 틀려도 **예산 초과는 발생하지 않는다.** 밴드는 덜 쓰는 방향으로만 열린다.

#### 밴드는 소형 카탈로그에서만 결정적이다 (측정 결과)

초안에서는 "argmin이면 항상 같은 조합이 나온다"고 단정했으나, 실측 결과 이는 **카탈로그가 작을 때만 참**이었다. 40편이면 조합 공간이 9만 개 규모라 200회 샘플링이 애초에 수렴하지 못하고, 따라서 argmin을 써도 호출마다 다른 답이 나온다.

동일 입력 100회 실행, 예산 30분 기준 실측:

| 카탈로그 | 밴드 | 고유 조합 | 최빈 점유 | 평균 언더슛 |
|---|---|---|---|---|
| 8편 | 0초 | 3종 | 95% | 10초 |
| 8편 | 30초 | 7종 | 21% | 21초 |
| 8편 | 60초 | 13종 | 15% | 39초 |
| 8편 | **90초** | **20종** | **10%** | **54초** |
| 8편 | 180초 | 25종 | 9% | 84초 |
| 20편 | 0초 | 21종 | 13% | 1초 |
| 20편 | **90초** | **91종** | **3%** | **43초** |
| 40편 | 0초 | 80종 | 3% | 1초 |
| 40편 | **90초** | **99종** | **2%** | **38초** |

밴드가 실제로 일하는 구간은 8편짜리 소형 카탈로그다. 여기서 밴드를 빼면 다양성이 **3종 / 최빈 95%**로 붕괴한다. 큐레이션 DB는 작게 출발하므로 밴드는 정확히 초기 제품 구간에서 필요하다.

**결론: 90초를 유지한다.** 다양성 곡선의 평탄 구간에 있고 비용은 30분 중 1분 미만이다. 30~120초 전체가 실용 범위이며, 180초를 넘으면 다양성 이득 없이 시간만 버린다.

카탈로그가 20편을 넘어서면 30~60초로 줄여 언더슛 20~25초를 회수할 수 있다. 다만 이는 카탈로그 규모별 적응형 밴드를 도입할 만큼의 이득은 아니다 — 상수 하나로 유지한다.

### 5.6 다양성의 실제 주력은 최근 시청 제외

날마다 답이 달라지는 주된 원인은 무작위성이 아니라 **후보 풀 자체가 달라지는 것**이다. 최근 세션의 영상을 하드 필터로 빼면 어제의 조합은 오늘 물리적으로 구성 불가능하다. 밴드 추출은 하루 안에서의 보조 장치다.

### 5.7 정렬과 활동 배치

선택된 영상을 길이 내림차순으로 정렬한다. 뒤로 갈수록 짧아져 세션이 자연스럽게 "줄어드는" 느낌을 주고, 마지막 영상이 짧아 종료 시 상실감이 적다.

```
[영상1] → 퀴즈 → [영상2] → 퀴즈 → [영상3] → 미션 카드
```

- 퀴즈는 **방금 본 그 영상에 딸린 문항**만 쓴다 (영상 메타데이터에 동봉)
- 브레이크당 최대 `QUIZ_ITEMS_PER_BREAK`(2)문항
- 미션 카드는 마지막 영상 뒤에만, 캐릭터의 미션 풀에서 최근 사용분을 제외하고 추출

### 5.8 난수 주입

`rng: () => number` 를 입력으로 받고 기본값은 `Math.random`이다. 테스트에서 시드 고정 RNG를 주입해 재현 가능한 검증을 한다.

## 6. 데이터 모델

```ts
type Video = {
  id: string
  characterIds: string[]
  durationSec: number
  title: string
  quizItems: QuizItem[]      // 2~3문항 동봉
}

type QuizItem = {
  id: string
  question: string
  choices: string[]
  answerIndex: number
}

type MissionCard = {
  id: string
  characterIds: string[]
  title: string
  description: string        // 오프라인 활동 지시
}

type PlanInput = {
  budgetSec: number
  characterId: string
  catalog: Video[]
  missions: MissionCard[]
  history: WatchHistory
  rng?: () => number
}

type WatchHistory = {
  recentSessions: {           // 최신순 정렬
    videoIds: string[]
    missionId: string | null
  }[]
}

type SessionPlan = {
  items: PlanItem[]          // video | quiz | mission 순서열
  videoIds: string[]
  plannedTotalSec: number
  underrunSec: number
}

type PlanResult =
  | { ok: true;  plan: SessionPlan }
  | { ok: false; reason: PlanFailureReason }
```

## 7. 실패 케이스

| 사유 코드 | 조건 | 앱 대응 |
|---|---|---|
| `BUDGET_TOO_SMALL` | 예산 < 최단 영상 + 미션 카드 | 부모에게 최소 권장 시간 안내 |
| `NO_VIDEOS_FOR_CHARACTER` | 해당 캐릭터 영상 0편 | 다른 캐릭터 선택 유도 |
| `CATALOG_EXHAUSTED` | 완화 2단계 후에도 조합 불가 | 카탈로그 보강 필요 (운영 알림) |

실패는 예외가 아니라 반환값이다. 호출부가 분기로 처리한다.

## 8. 불변식과 테스트

테스트는 `assert` 기반 셀프체크 하나로 둔다. 프레임워크를 도입하지 않는다.

**절대 불변식** (무작위 입력 1000케이스)

```
plannedTotalSec ≤ budgetSec        // 예외 없음
```

**다양성** (동일 입력 100회 실행)

이 지표가 이 설계의 성패를 결정한다. 다만 기준은 카탈로그 크기에 따라 달라진다. 8편짜리 카탈로그에서 고유 조합 8종을 요구하는 것은 알고리즘이 아니라 산수의 문제다.

| 카탈로그 | 고유 조합 수 | 최빈 조합 점유율 |
|---|---|---|
| 40편 | ≥ 12 | < 30% |
| 20편 | ≥ 8 | < 40% |
| 8편 | ≥ 3 | < 60% |

**대조군 필수**: 8편 카탈로그에서 밴드 0일 때 최빈 점유가 90%를 넘는지 함께 검증한다. 이것이 무너지면 밴드 설계의 전제 자체가 틀린 것이므로 회귀로 못 박는다.

**픽스처 함정**: 테스트 영상 길이를 30초 격자(300, 330, 360…)로 만들면 실제 카탈로그에는 존재하지 않는 동점 조합이 양산되어 다양성이 과대평가된다. 초 단위 임의값을 써야 한다.

기준 미달 시 `BAND_SEC`를 넓혀 재측정한다. 밴드를 넓혀도 개선되지 않으면 원인은 알고리즘이 아니라 카탈로그의 길이 분포 편중이다 (예: 대부분이 8분대에 몰려 있어 조합이 서로 치환 불가능한 경우). 이 경우 운영 측 대응 — 길이 다양성 확보 — 이 답이다.

**구조 검증**

```
영상 길이가 내림차순인가
퀴즈 브레이크 수 == 영상 수 - 1
미션 카드 정확히 1개, 항상 마지막
퀴즈 문항이 직전 영상에서 온 것인가
```

**동작 검증**

```
예산 부족 → BUDGET_TOO_SMALL
최근 시청 영상이 0단계에서 제외되는가
후보 고갈 시 완화가 발동하는가
시간 회계가 k개 영상에서 정확한가
```

## 9. 개인화 훅

지금은 붙이지 않되 자리는 만든다.

```ts
scoreVideo(video: Video, history: WatchHistory): number
```

MVP에서는 상수 1을 반환하고 셔플 가중치로만 쓰인다. 나중에 이 함수만 교체하면 개인화가 반영되며 **알고리즘 본체는 손댈 필요가 없다.**

초기에는 데이터가 0이므로 개인화할 재료가 없다. 규칙 기반 편성만으로 충분히 동작한다. 다만 로그는 1일차부터 쌓아야 한다. 나중에 개인화를 붙일 때 과거 데이터가 없으면 다시 몇 달을 기다려야 하기 때문이다.

**수집 이벤트**

모든 이벤트는 공통 필드를 갖는다: `eventId`, `occurredAt`, `sessionId`, `childId`, `schemaVersion`.

| 이벤트 | 추가 페이로드 |
|---|---|
| `session_started` | characterId, budgetSec, plannedTotalSec, plannedVideoIds |
| `video_started` | videoId, positionInPlan |
| `video_ended` | videoId, watchedSec, durationSec, completed |
| `quiz_answered` | videoId, quizItemId, correct, responseMs |
| `quiz_skipped` | videoId |
| `mission_shown` | missionId |
| `mission_completed` | missionId, completedBy |
| `session_ended` | actualScreenSec, exitReason |

`exitReason`: `plan_finished` | `child_left` | `parent_stopped` | `app_closed`

**초안에서 바뀐 점 세 가지**

1. **`video_started` 추가.** 초안에는 `video_completed`만 있었다. 앱이 죽거나 배터리가 나가면 종료 이벤트가 못 나가고, 그러면 그 영상을 틀었다는 사실 자체가 로그에서 사라진다. 시작 이벤트가 있어야 최소한 "시도했다"가 남는다.
2. **`video_completed` → `video_ended`.** 완주와 이탈을 한 이벤트로 담는다. `completed=false`일 때 `watchedSec`이 곧 이탈 지점이며, `durationSec`을 함께 실어 비율 계산에 조회가 필요 없게 한다.
3. **`mission_completed`는 지연 이벤트다.** 오프라인 활동이므로 앱을 끈 뒤에 완료되고 보통 다음 세션에서 회수된다. `occurredAt`이 같은 세션의 `session_ended`보다 늦은 것이 정상이며, **종료된 세션에 나중에 이벤트가 붙는 것을 스키마와 투영이 허용해야 한다.**

**전제**

- `eventId`는 호출부가 생성한다. `crypto.randomUUID`는 React Native에 없어 모듈이 만들면 플랫폼 지뢰가 된다.
- 오프라인 버퍼링 후 재전송될 수 있으므로 `eventId` 기준 멱등 처리가 전제다.
- 저장/동기화 계층은 이 모듈에 없다. 플랫폼마다 다르므로(AsyncStorage, SQLite, 서버) 앱이 꽂는다.

**투영: 로그 → 플래너 입력**

로그는 append-only 원본이고 플래너가 먹는 `WatchHistory`는 파생된 압축 뷰다. **둘을 따로 관리하면 반드시 어긋나므로 투영 함수를 유일한 경로로 둔다.**

```ts
projectHistory(events: LogEvent[], childId: string, sessions?: number): WatchHistory
```

세 가지 규칙이 중요하다.

- **이벤트 배열 순서를 신뢰하지 않는다.** 두 번 훑어 1회차에 `session_started`로 세션을 열고 2회차에 나머지를 붙인다. 오프라인 버퍼는 순서를 보장하지 않으며 미션 완료는 세션이 닫힌 뒤 들어온다.
- **`videoIds`는 계획된 영상이 아니라 실제로 튼 영상이다.** 아이가 1편만 보고 껐다면 나머지는 본 적이 없으므로 내일 제외할 이유가 없다.
- **`videoIds` 순서는 발생 시각 기준이다.** 입력 배열 순서에 의존하면 오프라인 버퍼가 뒤섞었을 때 시청 순서와 달라진다. 플래너는 집합으로만 쓰지만 순서를 시청 순서로 읽는 소비자가 나중에 반드시 생긴다.
- `session_started`가 유실된 세션은 신뢰하지 않고 버린다.

**스키마 검증 기준**

스키마가 충분한지는 "개인화가 나중에 물을 질문에 답할 수 있는가"로 판정한다. 다음 다섯 가지를 로그만으로 산출할 수 있어야 하며, 이를 테스트로 못 박는다.

| 질문 | 산출 방법 |
|---|---|
| 이 영상을 끝까지 봤나 / 어디서 이탈했나 | `video_ended.completed`, `watchedSec / durationSec` |
| 퀴즈 난이도가 맞나 | `quiz_answered.correct` 비율 |
| 아이가 활동에 참여하나 | `quiz_skipped` 대비 `quiz_answered` |
| 착지가 성공했나 | `mission_completed` / `mission_shown` |
| **부모와의 약속이 지켜졌나** | `session_ended.actualScreenSec ≤ session_started.budgetSec` |

마지막 항목이 제품의 성패 지표다.

## 10. 상수

| 상수 | 초기값 | 근거 |
|---|---|---|
| `QUIZ_SEC` | 40 | 2문항 응답 시간 추정 |
| `MISSION_CARD_SEC` | 20 | 카드 제시/읽기 시간 |
| `QUIZ_ITEMS_PER_BREAK` | 2 | 이탈 방지를 위한 최소 마찰 |
| `MAX_VIDEOS` | 5 | 잘게 쪼개진 조합 방지 |
| `K_ATTEMPTS` | 200 | 탐색 폭 |
| `BAND_SEC` | 90 | 출발점, 테스트로 튜닝 |
| `RECENT_SESSIONS` | 2 | 반복 방지 창 |

전부 한 곳에 모아 export한다. 실제 카탈로그 확보 후 재조정 대상이다.

## 11. 비범위 (YAGNI)

- 세션 도중 실시간 재편성 — 아이가 이탈하면 시간이 남을 뿐이며 안전한 방향이다
- 실제 개인화 모델 — 데이터 확보 후
- 여러 캐릭터 혼합 편성 — 단일 캐릭터로 시작
- 영상 수집/큐레이션 도구 — 초기엔 수동 등록
